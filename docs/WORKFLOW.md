# 개발 워크플로우 (matjip-share)

> 확정: 2026-07-04

## 핵심 원칙

1. **세로 슬라이스(vertical slice)로 반복** — 기능 하나를 DB부터 화면까지 관통시켜 끝낸다. 각 슬라이스가 끝나면 항상 "돌아가는 앱"이 남는다.
2. **경계 안쪽 로직에만 엄격한 TDD** — 순수 로직은 테스트 먼저. 외부 경계(지도 SDK, 실시간)는 강요하지 않는다.

## 슬라이스 절차

```
기능 단위로 반복:
  spec  →  plan  →  [test(red) → 구현(green) → refactor]  →  검증
                     └────────── TDD 루프 ──────────┘
```

- **spec**: 무엇을 만드는가 + 인수 기준(acceptance criteria)
- **plan**: 어떻게 만들 것인가 (파일/구조/순서)
- **TDD 루프**: 실패 테스트 → 통과 코드 → 리팩터
- **검증**: `/verify`로 실제 앱에서 동작 확인

## 테스트 전략 (테스트 피라미드)

| 대상 | 방식 | 도구 |
|------|------|------|
| 색상 배정, 별점 검증, 데이터 변환 등 **순수 로직** | **엄격한 TDD** (red→green→refactor) | Vitest |
| Supabase 쿼리, API 라우트 등 **경계** | **통합 테스트** (계약 검증, 먼저 안 써도 됨) | Vitest + 로컬 Supabase |
| 지도·핀 렌더링·실시간 반영 등 **UI/외부** | **E2E + 수동 검증** | Playwright + `/verify` |

원칙: **"테스트 먼저"를 로직엔 지키고, 지도 SDK엔 강요하지 않는다.**

## 도구 스택

- **단위/통합 테스트:** Vitest + React Testing Library
- **E2E:** Playwright
- **Supabase 테스트:** 로컬 Supabase(Docker) 대상 통합 테스트 → 실제 스키마 검증
- **Git:** 슬라이스마다 브랜치 → 작은 커밋 → 검증 후 머지

## 슬라이스의 "완료(Done)" 정의

1. spec에 **인수 기준**이 있고
2. 그 기준이 **테스트로 존재**하고 (로직은 단위, 흐름은 E2E)
3. 테스트가 **초록**이고
4. `/verify`로 **실제 앱에서 동작 확인**됨

## 예상 슬라이스 순서 (초안)

1. ~~이름 입력 → 고유 색상 배정~~ ✅ 완료 (2026-07-04)
2. 카카오맵 표시
3. 맛집 핀 추가 (카카오 로컬 장소 검색 → 별점 → 저장 → 내 색상 핀)
4. 실시간 공유 (Supabase Realtime 구독)
